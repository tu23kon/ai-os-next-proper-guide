AI OS Idea Guide

The design ideas behind a personal "AI operating system": one place that takes your tasks, picks a free AI model that is working right now, runs the work safely, checks the result with a second model, and remembers progress so nothing is lost. This guide describes ideas, not code — build your own version in any language and change it to fit your needs.

1. The core idea

The OS decides; agents only do the work. An "agent" is a worker that gets a task and returns a result. It never chooses which model is used, which tools it gets, whether a result is accepted, or what happens next. All of that belongs to the OS, which decides from things it observed itself — never from what an agent claims.

Why: models make mistakes and web pages can contain text that tries to steer them ("ignore your instructions…"). If the worker can't change the rules, a confused or manipulated worker can only produce a bad result — which the OS then catches — not take over the system.

Other ideas that follow from this:

  • Free first: use many free AI APIs together, so when one is down or out of quota, another takes over.
  • Nothing is lost: every step is saved to disk, so a crash or restart continues where it stopped.
  • Trust nothing from outside: web text, model replies and file contents are data, never instructions.
  • The human stays in control: logins, risky actions and preferences are the user's decisions.

3. Model access: catalog, health, router

Catalog

A list of AI providers with free tiers (several offer free API access to good models). For each: name, API style (most speak the "OpenAI-compatible" format), base URL, which environment variable holds its key, default model, and what it is good at. Keys live only in a local .env file that is never shared or committed.

Health

The OS sends each provider a tiny test request ("probe") and remembers the outcome with an expiry time:

StateMeaningExample expiry
HEALTHYanswered correctly24 h
DEGRADEDtemporary problem (rate limit, timeout, server error) — retry soon30 min
BROKENpermanent problem (bad key, unknown model) — needs a settings change24 h
UNASSESSEDno fresh result yet—

Probing runs in the background at startup so the system is usable immediately. Results are saved to a status file, so a restart doesn't re-probe everything.

Router

For each model call: take the providers that are configured and not cooling down, order them (healthy first, then degraded, best match for the task's capability first), and try them one by one. On a temporary error, put that provider on a short cooldown and move to the next; on a permanent error, take it out of the pool. Record why each provider was chosen or skipped.

for provider in ordered_candidates(task.capability):
    try:
        reply = provider.call(request)
        mark_success(provider)
        return reply, provider.name, reply.model     # who really answered
    except TemporaryError:
        cooldown(provider, minutes=5); continue
    except PermanentError:
        remove_from_pool(provider); continue
raise NoProviderAvailable(decision_log)
Why: free tiers are unreliable one by one but reliable together. Keep a safety rule: if every provider looks broken, keep them rather than emptying the pool, so the system never locks itself out.

4. Tasks and their life cycle

Every piece of work is a task with a goal, a required capability (general, reasoning, coding, research, browser…), an attempt limit and a status. Status changes follow a strict table; anything not in it is rejected:

QUEUED → PLANNING → ASSIGNED → RUNNING → CHECKPOINTED → COMPLETED
                                   ↘ BLOCKED  (needs a human)  → back to QUEUED
                                   ↘ FAILED   (recovery decides) → back to QUEUED or stays failed
CHECKPOINTED → back to QUEUED if review asks for rework
COMPLETED and CANCELLED are final.

A task can only be completed from CHECKPOINTED, so every accepted result is saved before it counts. Tasks can be submitted to run in the background; the user asks for status or the result later.

5. Checkpoints and leases

Checkpoint: after every meaningful step, write the full task state to a file (write to a temp file, then rename — so a crash never leaves half a file). Store a hash or integrity check so a damaged or tampered checkpoint is detected and refused.

Lease: before working on a task, a worker process creates a lock file for it, exclusively. The lease has an owner, an expiry time and a fencing token — a number that goes up with every new holder. If a process freezes and its lease expires, another may take over; when the old one wakes up, its next checkpoint sees a newer token and it stops without writing.

Why: this makes it safe to run several windows/processes at once and to restart at any time. Two owners can never write the same task.

Startup recovery: on start, look for tasks a stopped process left mid-way (running, accepted-but-not-reviewed, or a login the user finished). Resume each through the normal path — take its lease, validate its checkpoint, let the recovery policy decide. Every restart uses up an attempt, so recovery can never loop forever.

6. Failures and recovery

The OS classifies each failure from what it observed (not from the agent's explanation), then decides:

Failure classTypical decision
Provider trouble (rate limit, outage)retry; the router will pick another provider
Agent's fault (bad output, crashed)retry, but after 2 failures exclude that agent and assign another
Timeout / deadline passedstop or retry depending on the deadline
Needs a human (login, approval)BLOCKED — wait, never guess
Not allowed / invalid tasknever retried automatically

Cancellation is a first-class operation: it saves a checkpoint first, then aborts running work (including web requests), and only the process holding the lease can do it.

7. Independent review

When an agent returns a result, a reviewer agent checks it before it's accepted: does it actually answer the goal, is it complete, does it follow the user's preferences? Rules that keep review honest:

  • A reviewer never reviews work it produced itself.
  • It receives the task and the result as data, and must answer in a strict format (accept / rework + reasons). An unreadable review counts as a failure, not as "accepted".
  • For browser or research work, the reviewer judges against the OS's own record of what really happened (pages fetched, actions taken), not the agent's story.
  • Exact-output contracts: if the user says "Return exactly X and do nothing else", the OS checks the answer itself, character by character. No model decides that.

8. Plans (multi-step work)

A plan is a short ordered list of steps (e.g. at most 5) that the user asks for. The OS runs one step at a time, each as a normal task (with review, checkpoints and recovery), waits for it to finish, and only then starts the next. A later step receives earlier results only as bounded data written into its goal. Agents can't create, change or extend a plan.

Why: long autonomous chains drift and multiply errors. Short, user-owned plans keep big jobs predictable and resumable (a plan can be paused and resumed after a restart).

9. Web research, safely

Research is mostly deterministic: the OS turns the task into a short search query (removing instructions, URLs and anything that tries to steer the system), runs one search, fetches the top results in order, and keeps for every source how it was found. A model then condenses each source and writes the final answer with citations — it can only cite what the tools actually returned.

Search sources are pluggable (keyless ones like Wikipedia or a self-hosted SearXNG, or keyed APIs like Exa/Tavily) and off by default, because searching sends your query to a third party.

Fetching pages safely (important if you build this):

  • Only http/https; block local and private network addresses (so a page can't trick the OS into calling your router or internal services).
  • Resolve DNS, check the address, then connect to that exact address (prevents "DNS rebinding"). Re-check every redirect.
  • Read at most N bytes; convert HTML to text without running scripts.
  • Send fixed headers only — never cookies, auth headers or anything from your environment.
  • Mark all web text as untrusted wherever it leaves the tool, and redact anything that looks like a secret.

A real browser (e.g. Playwright) is an optional extra tool for pages that need JavaScript, granted only to tasks that need it.

10. Human steps: logins and actions

When a task reaches a site that needs the user to sign in, the OS pauses the task, shows a safe instruction ("please sign in to example.com"), and waits for an explicit "done" from the user. It never asks for, stores or shows passwords, cookies or tokens — only the site's origin is kept. The same pattern works for any step only a human can do (approve a payment, solve a captcha, confirm a risky action).

11. Preferences and learning

The user can set preferences ("answers short", "use British spelling", "never use provider X"). Levels of trust, highest first:

  1. What the user stated explicitly
  2. Instructions in the current task (can be promoted to a lasting preference on request)
  3. Learned preferences — lowest trust

Agents only see resolved preferences and may propose observations. A learned preference becomes active only after the user corrects the same thing several times, and it can never override something the user said. The user can view, confirm, reject or delete any of them.

12. Honest bookkeeping

  • Attribution: record which provider and model really answered, taken from the API response metadata — never from what the model says about itself.
  • Context usage: track tokens only when the provider reports them; warn at ~80% of the model's limit. If it's unknown, show "unknown", don't estimate.
  • No secrets in logs: routing summaries, status reports and errors never contain keys or account IDs.

13. Optional module: website builder

The same machinery can run a bigger pipeline as a chain of reviewed stages, for example: brief → find reference sites → capture and analyse them (layout, colours, type) → design spec → build → automated tests → review → iterate. Each stage is a task with its own checkpoint, so a long build survives restarts. Text taken from reference sites is treated as untrusted data (it may contain instructions aimed at the model).

14. The interface (MCP tools)

The OS can run as an MCP server (Model Context Protocol), so any MCP-capable chat app or code editor can use it. A small, clear tool set works well:

ToolWhat it does
ask_modelone quick routed model call
task_run / task_submitrun a task now / in the background
task_status / task_resultcheck progress / get the reviewed result
task_resume / task_cancel / task_unblockcontrol a task
task_login_complete / task_human_action_completetell the OS a human step is done
plan_start / plan_status / plan_resume / plan_resultmulti-step plans
web_search / web_fetch / web_researchsafe web access
provider_statuswhich providers are configured, healthy and routable (never shows keys)

Tools that act on a task should only work for tasks that server instance owns.

15. Safety rules that run through everything

  1. Outside text (web, files, model replies) is data, never instructions.
  2. Keys stay in a local env file; they never appear in logs, results, errors or checkpoints.
  3. The OS checks results itself wherever a rule can be checked without a model.
  4. Every limit is explicit: attempts, tool calls, bytes read, time, steps.
  5. Pause for humans instead of guessing. Never store login data.
  6. Tests run offline with fake providers and fake keys, from an empty folder, so a real key can never be used or leaked by a test.

16. How to build your own, step by step

Any language works (the ideas were first built in TypeScript/Node). A sensible order, each step useful on its own:

  1. One provider, one call. Read a key from .env, send a prompt, print the answer.
  2. Catalog + router. Add 3–5 free providers in the OpenAI-compatible format; try them in order with failover.
  3. Health probes with expiry times, saved to a status file; run them in the background.
  4. Tasks + life cycle table + checkpoints to disk. Make "kill the process mid-task, restart, it continues" work.
  5. Reviewer with a strict reply format, never reviewing its own work.
  6. Recovery policy (failure classes, attempt limits, agent exclusion) and leases.
  7. Safe web fetch + search + research with sources.
  8. MCP server so your chat app or editor can use it.
  9. Human steps, preferences, plans — then bigger modules like the website builder.
Tips: write the tests with a mock provider first (it's much faster and free); keep each module small; and log the router's decisions — "why did it pick this model?" is the question you'll ask most.
